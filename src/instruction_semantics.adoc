[[ame-common-instruction-semantics]]
=== Common instruction semantics

[[ame-common-operand-validation]]
==== Operand validation and exception priority

For every AME instruction, the applicable validation checks occur in the
following architectural order unless its detailed definition states otherwise:

. State-access checks in <<ame-common-state-access>> complete first.
. Every encoded register specifier and every instruction-specific constraint
  determined solely from encoded fields is checked before the addressed AME
  register or datatype state is read.  Failure raises an Illegal Instruction
  exception.
. The exact operation/datatype tuple is then checked.  An unsupported tuple
  sets `amestatus.UN` and returns without a destination write; it is not a
  synchronous exception.  Derived group geometry is not interpreted for an
  unsupported tuple.
. For a supported tuple, operands are formed under
  <<operand-formation,the operand-formation rules>> and
  every derived base alignment and complete physical-register span is checked,
  including any derived accumulator span.  A zero span, misalignment, or span
  outside the implemented register file raises an Illegal Instruction
  exception.
. Only after those checks may operand data be accessed and the instruction
  commit under <<norm:ame_source_snapshot,the source-snapshot rule>> and
  <<norm:ame_atomic_register_writeback,the atomic-writeback rule>>.

[[register-group-overlap]]
==== Register group overlap and atomic writeback

[#norm:ame_register_group_overlap]#Unless an instruction explicitly states an
overlap restriction, any source `M` or `Acc` register group may overlap any
destination register group, including complete overlap where the base register
numbers are equal.#

[#norm:ame_source_snapshot]#All source register values, source datatype values,
scalar operands, and index operands are read from the architectural state that
exists immediately before the instruction begins.# Destination overlap does
not alter that source snapshot unless an instruction explicitly defines an
ordered destination update.

[#norm:ame_atomic_register_writeback]#For register-only AME instructions, all
destination `M`, `Md`, `Acc`, and `Ad` writes, together with accrued
`amefflags` and `amexsat` updates, become architecturally visible as one commit
only after the instruction completes successfully.#

[#norm:ame_register_exception_atomicity]#If a register-only AME instruction
raises a synchronous exception, none of its destination writes or accrued
`amefflags` or `amexsat` updates occur; only architectural trap state written by
exception handling may change.#

[[ame-common-datatype-support]]
==== Datatype tuple support

An *instruction datatype tuple* is the operation together with every datatype the
instruction interprets as a type in producing its result, regardless of where
each one comes from: the `Md` and `Ad` descriptors of the operands it interprets,
`CSR[amestype]` for a CSR-typed scalar, and any datatype an instruction supplies
explicitly in an X register.  A descriptor that an instruction only copies,
replaces wholesale, or ignores is not a required datatype.

Two datatype descriptors *specify the same datatype* when they agree on class,
size, and signedness.  The rounding-mode and saturation fields are not compared,
so descriptors differing only in those fields specify the same datatype.

[#norm:ame_op_supported_contract]#An instruction datatype tuple is unsupported
when a required datatype is zero or unknown, the operation is not implemented,
the exact operation/datatype combination is not supported, or a datatype
definition lacks a semantic capability required by the instruction's
`Operation` and applicable family rules.#
An unsupported tuple sets `amestatus.UN` and leaves every destination register
unchanged; it does not raise a synchronous exception.

Standard datatypes obtain their arithmetic, comparison, conversion, rounding,
raw-bit, sign, zero, and status-flag behavior from this specification.  An
accepted tuple containing a custom datatype shall have definitions for every
such capability used by its `Operation`, including any required ordering,
semantic zero, source-to-destination conversion, raw-bit or sign
interpretation, and result or flag behavior; otherwise the tuple is
unsupported.

[#norm:ame_op_supported_defined_result]#Once an implementation accepts an
operation/datatype tuple, the result is the mathematical operation stated by
the instruction, interpreted and converted according to the common datatype
rules and applicable instruction-family semantics in this specification.#

[#norm:ame_op_precondition]#No source data is consumed and no destination data
is produced until the encoded indices and required datatype tuple have passed
their common validation checks.#

[#norm:ame_op_result_width]#An element result is represented in the destination
datatype.  Bits outside that datatype representation are not architectural
state and cannot affect a later AME operation.#

Datatype applicability is therefore determined by exact operation/datatype
capability, not by a global operand-class whitelist.

[[ame-common-integer]]
==== Standard integer operation semantics

The *Rounding mode* field applies to integer operations whose exact
mathematical intermediate result has fraction bits below the LSB of the
destination datatype.  Let `v` be the
exact intermediate result and `d` the number of fraction bits discarded when
producing the destination-width integer result.  `v` is treated as a two's
complement value and `>>` denotes an arithmetic right shift.  When `d == 1`,
the term `v[d-2:0]` is treated as zero.  The rounded result is
selected by the destination datatype's rounding mode:

|===
| Encoding | Mode | Rounded result

| `00`
| RNU (round-to-nearest-up)
| `(v >> d) + v[d-1]`

| `01`
| RNE (round-to-nearest-even)
| `(v >> d) + r`, where `r = 1` if `v[d-1] == 1` and `(v[d-2:0] != 0 or
v[d] == 1)`, else `r = 0`

| `10`
| RDN (round-down, truncate)
| `v >> d`

| `11`
| ROD (round-to-odd, jam)
| `(v >> d) {vbar} (v[d-1:0] != 0)`

|===

Operations whose exact result is already integral are unaffected by the
rounding mode.  The rounding mode does not apply to floating-point datatypes,
whose rounding follows the IEEE floating-point class rules.

[[ame-operation-notation]]
==== Operation notation

In an architectural `Operation`, `A` denotes the formed M-register source
selected by `ms1`, or the sole M-register source named `ms` or `ms2` when there
is no `ms1`. `B` denotes `ms2` in a two-source form, `D` denotes `md`, `C`
denotes an accumulator operand, and `c` denotes an instruction-defined scalar
value. The applicable common contract defines the formula's element or square
domain and the meaning of its index variables. Unless that contract defines an
ordered update, `D` or `C` on the right-hand side denotes the pre-instruction
destination value under
<<norm:ame_source_snapshot,the pre-instruction source snapshot rule>>.

`x mod y` denotes the non-negative remainder of `x` divided by `y`, so a negative
`x` yields a result in `[0, y)`.  `x[h:l]` denotes a bit field of `x`'s
representation, and `zero_extend_XLEN(v)` denotes `v` zero-extended to XLEN bits.
`zero_resize(v, w)` denotes the `w`-bit value formed from `v`'s bit
representation, which shall have a defined width: zero-extended when `w` exceeds
that width, otherwise its low `w` bits.

`M[r]` and `Acc[r]` denote physical registers rather than formed operands.
`raw_bits(...)` denotes the uninterpreted bit pattern of its operand: a named
physical register, a contiguous register range, or a single element of a formed
operand.  It bypasses datatype interpretation — the bits are transferred as they
stand, with no conversion, rounding, saturation, NaN quieting, or zero-sign
normalization, and with no `amefflags` or `amexsat` update.  Applied to a
physical register or register range it also bypasses operand formation; applied
to an element of a formed operand, operand formation still locates that element
while the value itself remains uninterpreted.  An element's raw bits are its
datatype's `sizeof(dtype)`-bit representation with bit 0 the least-significant
bit of that datatype, that is, the element's field in the row-major
interoperability bit string of <<ame-common-memory,the interoperability transfer
rules>>.  Used as an assignment target, `raw_bits(x) = v` writes `v` bit for bit
into that representation without interpreting it; `v` shall have the same width
as the representation.

=== Instruction-family semantics

[[ame-common-matmul]]
==== 2-dimensional matrix multiply operations

Every logical source square is `N x N`.  Square `s` of the two formed source
operands is paired as `A[s]` and `B[s]`; the accumulator is one `N x N` square,
so each output element folds `N_sq * N` scalar products.  Transposition applies
within each paired square:

[source]
--
ordinary(i,j,s,q)    = A[s][i,q] * B[s][q,j]
transpose-A(i,j,s,q) = A[s][q,i] * B[s][q,j]
transpose-B(i,j,s,q) = A[s][i,q] * B[s][j,q]
--

For each output element, the implementation uses a fixed, deterministic
permutation of all `(s,q)` terms.  It seeds the fold with the pre-instruction
accumulator element and adds or subtracts each product in that order; it does
not first reduce the products separately.  The accepted tuple defines the
typed multiplication and accumulation.  The implementation shall document its
overflow, saturation, floating-point rounding, and optional fused-product
behavior, which shall be deterministic for that tuple.  Register encodings are
never accumulated as untyped bit vectors, and the fold is never implicitly
seeded with zero.


[[ame-common-arithmetic]]
==== 1-dimensional elementwise operations

Each instruction applies the `Operation` defined on its detailed instruction
page independently to every logical element of every square selected by operand
formation, as required by <<norm:ame_nsq_1d,the common operand-formation rule>>.

Among standard datatypes, `mexp2.ew`, `mlog2.ew`, `mcos.ew`, `msin.ew`,
`mtanh.ew`, `mrec.ew`, `mrsqrt.ew`, `msqrt.ew`, and the `mfrint*.ew` family
require floating-point source and destination datatypes.  For the
`mlog2sub.ew` and `msublog2.ew` families, including their `.ew.x` forms, the
operand of `log2`, and the destination, are standard floating-point datatypes;
the bias is governed by the exact tuple's conversion and subtraction
capabilities.  Custom tuples may define these operations under
<<ame-common-datatype-support,the exact-tuple capability contract>>.
Standard floating-point operations additionally follow
<<ame-common-floating-point,the standard floating-point operation semantics>>.

For standard integer arithmetic, the mathematical expression is evaluated
without intermediate truncation and converted once to the destination integer
datatype.  A saturating destination clamps an out-of-range result and sets
`amexsat.SAT`; a non-saturating destination retains the low destination-width
bits.  `mhdiff.ew`, `mhdiff.ew.x`, `mmean.ew`, and `mmean.ew.x` round fraction
bits below the destination LSB according to
<<ame-common-integer,the common standard-integer rounding rules>> before that
conversion.  Custom
datatype tuples may define different conversion rules.

[[ame-common-floating-point]]
==== Standard floating-point operation semantics

This subsection supplies the default result, rounding, and flag behavior for
accepted standard floating-point tuples of the 1-dimensional elementwise
operations in <<ame-common-arithmetic>> and of the prefix, reduction, and
scatter instructions whose detailed definitions add floating-point rules.  It
does not apply to raw-bit behavior and does not override the
implementation-defined product and accumulation behavior of
<<ame-common-matmul>>.

AME floating-point rounding is selected by the destination datatype; AME has no
global dynamic rounding mode analogous to `fcsr.FRM`.  Standard floating-point
operations accrue IEEE exception flags in `amefflags` and do not modify
`fflags`; they OR the accrued flags into `amefflags` at the commit defined by
<<norm:ame_atomic_register_writeback,the atomic register-writeback rule>>.

[#norm:ame_fp_special_values]
Unless the detailed instruction states an exception, an operation covered by
this subsection follows its exact mathematical expression and rounds a finite
result once using the destination datatype's rounding mode.  Any NaN input or
invalid operation produces the destination datatype's canonical quiet NaN; a
signaling NaN is quieted.  Invalid operations include indeterminate infinity
addition or subtraction and zero multiplied by infinity.  Ordered comparisons,
including those used as numeric predicates, instead follow their detailed
instruction definitions.

Floating-point exceptional conditions are data results after tuple acceptance:
they neither trap nor set `amestatus.UN`.  If the destination cannot represent a
required infinity, the result saturates to the appropriate signed minimum or
maximum; if it cannot represent a required NaN, the tuple is unsupported.

For standard floating-point datatypes, `amefflags` uses the same five accrued
exception classes as RISC-V `fflags`, with tininess detected after rounding:

* `NV` is set for a signaling NaN or an invalid operation, including an
  infinity-minus-itself form, zero multiplied by infinity, a finite negative
  square root, or an invalid floating-point-to-integer conversion.  Propagating
  a quiet NaN alone does not set `NV`.
* `DZ` is set when an exact infinite result arises from finite inputs because
  of a pole at zero, including reciprocal or reciprocal-square-root of zero
  and `log2(±0)`.
* `OF` is set when the rounded result's magnitude exceeds the destination's
  finite range.  Such a result also sets `NX`.
* `UF` is set when the result is tiny after rounding and inexact.  Such a
  result also sets `NX`.
* `NX` is set whenever the delivered finite result differs from the exact
  mathematical result because of rounding, including an implementation-defined
  approximation that is not exact.

Exact operations and exact conversions set none of these flags.  A custom
floating-point datatype definition must specify equivalent flag conditions
for every supported tuple that can update `amefflags`; otherwise that tuple is
unsupported.

[[ame-common-scalar-operands]]
==== Scalars

For a CSR-typed-scalar `.ew.x` instruction, let
`scalar_dtype = CSR[amestype]`.  The required tuple is (`scalar_dtype`,
`Md[ms2]`, `Md[md]`), and the exact tuple determines whether that combination is
supported; a zero, unknown, or unsupported descriptor makes it unsupported.  The
instruction uses the low `sizeof(scalar_dtype)` bits of the X-register operand
when XLEN is at least that width and ignores higher bits.  When
`sizeof(scalar_dtype)` exceeds XLEN, it extends the X-register bit pattern to
that width, sign-extending when `scalar_dtype` is a signed integer datatype and
zero-extending otherwise.  It interprets the resulting bits using `scalar_dtype` to form
`c`.  There is no implicit conversion to `Md[ms2]`: `c` participates in the
detailed `Operation` as the exact value that `scalar_dtype` denotes.  Where that
`Operation` combines `c` arithmetically with element data, the expression is
evaluated without an intermediate conversion and its result is converted once to
`Md[md]` under the family rules selected by `Md[ms2]` and `Md[md]`; where `c`
only selects an index, offset, shift amount, or slot, no conversion of `c`
occurs.  If the exact tuple does not define how a `scalar_dtype` value
participates in that `Operation` together with `Md[ms2]` and `Md[md]` — in
particular when they belong to different datatype families — the tuple is
unsupported.

When an instruction uses `c` as an index or offset whose out-of-range value is
architecturally visible, the tuple is unsupported unless `scalar_dtype` can
represent every value in the range that instruction defines.  An operand that the
instruction reduces instead — a shift amount taken modulo the element width, or a
selector taken from low bits — carries no such requirement, because the reduction
makes every value of `c` well defined.

Every X-register scalar operand of an `.ew.x` instruction is CSR-typed,
including shift amounts, indices, offsets, and packed-slot selectors.  An
instruction may constrain the datatypes it accepts and may use only part of the
interpreted value — the low `log2(pack_factor)` bits of a slot selector, a shift
amount reduced modulo the element width — but it always derives the operand's
datatype from `CSR[amestype]`.

Control scalars outside the elementwise instructions, such as memory strides,
remain the signed or unsigned integer quantities defined by their instruction.
They do not use `amestype` or undergo AME datatype conversion.
