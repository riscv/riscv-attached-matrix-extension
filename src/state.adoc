[[state]]
== AME State
:imagesdir: ../images

AME architectural state includes

* <<ame:doc:param:AME_NUM_M_REGS,AME_NUM_M_REGS>> general-purpose matrix registers (`M`)
* <<ame:doc:param:AME_NUM_M_REGS,AME_NUM_M_REGS>> datatype registers for the general-purpose registers (`Md`)
* <<ame:doc:param:AME_NUM_ACC_REGS,AME_NUM_ACC_REGS>> accumulator register(s) (`Acc`)
* <<ame:doc:param:AME_NUM_ACC_REGS,AME_NUM_ACC_REGS>> datatype registers for the accumulation register(s) (`Ad`)

.AME register state
image::ztt_regfiles.svg[Register state]

[NOTE]
--
Both <<ame:doc:param:AME_NUM_M_REGS,AME_NUM_M_REGS>> and <<ame:doc:param:AME_NUM_ACC_REGS,AME_NUM_ACC_REGS>>
are parameters that affect binary compatibility.

Code written for `AME_NUM_M_REGS = 32` will not run on an implementation that chooses `AME_NUM_M_REGS = 16`.

Code written for `AME_NUM_ACC_REGS = R` will not run on an implementation that chooses `AME_NUM_ACC_REGS` less than `R`.

Conversely, code written for smaller values of
<<ame:doc:param:AME_NUM_M_REGS,AME_NUM_M_REGS>>/<<ame:doc:param:AME_NUM_ACC_REGS,AME_NUM_ACC_REGS>>
will run on an implementation that chooses a larger value.
--

=== Registers

==== Matrix registers (`M0-M15` or `M0-M31`)

.Matrix register state summary
[cols="1,3"]
|===
h| Number of registers a| <<ame:doc:param:AME_NUM_M_REGS,AME_NUM_M_REGS>>
h| Width of a register a| <<ame:doc:param:AME_UNIT_DATATYPE_SIZE,AME_UNIT_DATATYPE_SIZE>> * <<ame:doc:param:AME_NELEM,AME_NELEM>>
|===

AME adds an implementation-defined number of general‑purpose registers.
The number is determined by <<ame:doc:param:AME_NUM_M_REGS,AME_NUM_M_REGS>> and may be either 16 or 32.
Code referencing `M16`–`M31` (that is, assuming <<ame:doc:param:AME_NUM_M_REGS,AME_NUM_M_REGS>> is 32)
is not compatible with an implementation that chooses <<ame:doc:param:AME_NUM_M_REGS,AME_NUM_M_REGS>> of 16.

The width of `M` register is implementation-defined, and is equal to
<<ame:doc:param:AME_UNIT_DATATYPE_SIZE,AME_UNIT_DATATYPE_SIZE>> * <<ame:doc:param:AME_NELEM,AME_NELEM>>.
The layout of data in an `M` register is also implementation-defined.  Two portable
routes exist with distinct semantics.

To access the register's data as *logical elements of its programmed datatype*, use the
interoperability load and store instructions, which convert to a standard layout (
  <<ame:doc:inst:mls_rm,mls.rm>>,
  <<ame:doc:inst:mls_cm,mls.cm>>,
  <<ame:doc:inst:mss_rm,mss.rm>>,
  and/or <<ame:doc:inst:mss_cm,mss.cm>>
).

To move a register's *image* without regard to its programmed datatype — for register
spilling, context switching, and calling conventions — use
<<ame:doc:inst:mls_1r,mls.1r>> and <<ame:doc:inst:mss_1r,mss.1r>>.  Their transfer is
row-major at a fixed element size of
<<ame:doc:param:AME_UNIT_DATATYPE_SIZE,AME_UNIT_DATATYPE_SIZE>>, so it does not depend on
the internal layout either, and it neither reads nor requires a supported datatype.

==== Matrix datatype registers (`Md0-Md15` or `Md0-Md31`)

AME adds an implementation-defined number of 32-bit `Md` registers used to identify
the datatype of square elements.
The number of `Md` registers equals <<ame:doc:param:AME_NUM_M_REGS,AME_NUM_M_REGS>> (16 or 32), matching the number of `M` registers.

`Md` registers can only be read or written with the <<ame:doc:inst:mgettyp,mgettyp>> and
<<ame:doc:inst:msettyp,msettyp>> instructions.

Each `Md` register specifies the element datatype for the `M` register with the same index.

The value of an `Md` is sticky, even if it is otherwise unused due to register grouping.
For example, if registers 0 and 1 are grouped, a value written (via <<ame:doc:inst:msettyp,msettyp>>)
into `Md[1]` will be retained even though it has no effect on the group.

The encoding format of `Md` datatypes is specified in
<<datatype-descriptor-encoding,the datatype descriptor encoding>>.

==== Accumulator registers (`Acc0` through `Acc[AME_NUM_ACC_REGS-1]`)

AME adds an implementation-defined number of matrix accumulator registers.
The number is determined by <<ame:doc:param:AME_NUM_ACC_REGS,AME_NUM_ACC_REGS>> and may be 1, 2, 4, 8, or 16.
Software written for <<ame:doc:param:AME_NUM_ACC_REGS,AME_NUM_ACC_REGS>> greater than an implementation
implements will not run on that implementation.

Any instruction that specifies an unimplemented `Acc` or `Ad` register
(index greater than or equal to `AME_NUM_ACC_REGS`) raises an
`Illegal Instruction` exception.

The architectural register file may contain fewer than 32 accumulators, but
instruction encodings use standard 5-bit register slots for `Acc` and `Ad`
specifiers.  This keeps the instruction formats uniform with M and integer
register operands; it does not require 32 physical accumulator registers.

An `Acc` register must be large enough to hold the largest representable square for an implementation given the supported datatypes.
Note, this is unlike the `M` registers, which may be grouped to hold a single square.

`Acc` registers are the destination of all AME matrix multiply instructions.
`Acc` registers can also be source or destination of AME move instructions.

==== Accumulator datatype registers (`Ad0` through `Ad[AME_NUM_ACC_REGS-1]`)

AME adds an implementation-defined number of 32-bit accumulator datatype registers.
The number is determined by <<ame:doc:param:AME_NUM_ACC_REGS,AME_NUM_ACC_REGS>> and may be 1, 2, 4, 8, or 16 (same as the `Acc` registers).

`Ad` registers can only be read or written with the <<ame:doc:inst:agettyp,agettyp>> and <<ame:doc:inst:asettyp,asettyp>> instructions.

Each `Ad` register specifies the element datatype for the `Acc` register with the same index.

The encoding format of `Ad` datatypes is identical to the format for `Md` and
is specified in
<<datatype-descriptor-encoding,the datatype descriptor encoding>>.

=== Control and status registers (CSRs)

AME adds seven CSRs.

The addresses below are provisional allocations in the corresponding
user-level custom read/write and read-only CSR ranges.  A future ratified
version may assign different standard CSR addresses.

|===
| CSR | Address | Description

| <<ame:doc:csr:amenlen,amenlen>>
| `CC0`
| AME tile side length

| <<ame:doc:csr:ameudsz,ameudsz>>
| `CC1`
| AME unit datatype size in bits

| <<ame:doc:csr:amestype,amestype>>
| `CC2`
| Datatype used to interpret scalar operands supplied in `X` registers

| <<ame:doc:csr:ameown,ameown>>
| `CC3`
| Ownership of the AME backend

| <<ame:doc:csr:amefflags,amefflags>>
| `CC4`
| Accrued AME floating-point exception flags

| <<ame:doc:csr:amexsat,amexsat>>
| `CC5`
| AME fixed-point saturation flag

| <<ame:doc:csr:amestatus,amestatus>>
| `800`
| Status of the AME extension

|===

`amestype` and `amestatus` are backend context state. `amenlen` and
`ameudsz` report implementation capabilities. `ameown` reports ownership.

[#ame:doc:csr:ameown]
==== ameown

`ameown` is a read-only CSR that reports whether the current software execution
context owns the entire AME backend. It may be read when every applicable `MS`
field is non-Off, regardless of ownership. Any CSR instruction that attempts
to write `ameown` raises an illegal-instruction exception.

|===
| Field | Location | Description

| OWNED
| `0`
| One when the current context owns the backend; zero otherwise

| RESERVED
| `XLEN-1:1`
| Reads as zero

|===

`ameown.OWNED` is set when `ame.acquire` newly grants ownership and cleared by
`ame.release`. A failed acquire does not change it. It resets to zero.
The save-and-restore protocol for this field is defined in
<<ame-backend-context-switch>>.

[#ame:doc:csr:amestype]
==== amestype

Selects the AME datatype used to interpret an X-register operand when an
instruction declares a *CSR-typed scalar* operand.  The encoding is the same
32-bit datatype encoding used by `Md` registers.  A value of zero means that
the scalar datatype is uninitialized; an unsupported scalar datatype, or an
unsupported exact operation/datatype tuple, sets `amestatus.UN` and leaves the
destination unchanged. Software may write any 32-bit encoding; unsupported
encodings are retained in the CSR and are rejected when a CSR-typed scalar
instruction uses them.

Every X-register scalar operand of an elementwise (`.ew.x`) instruction is typed
by this CSR, including shift amounts, indices, offsets, and packed-slot
selectors.  Control scalars outside the elementwise instructions, such as memory
strides, retain their fixed integer semantics and do not read this CSR.  An
instruction that supplies a datatype explicitly in an X register, such as
<<ame:doc:inst:mbcast_m_x,mbcast.m.x>>, uses that datatype instead.

The CSR resets to zero. It is backend context state and must be saved and
restored with the AME state when software changes execution context.
When XLEN is greater than 32, bits `XLEN-1:32` are WPRI and read as zero.
Consequently, a read of `amestype` zero-extends `VALUE` to XLEN.

|===
| Field | Location | Description

| VALUE
| `31:0`
| AME datatype encoding for CSR-typed scalar X operands

| RESERVED
| `XLEN-1:32` (when `XLEN > 32`)
| WPRI; reads as zero

|===

[#ame:doc:csr:amenlen]
==== amenlen

Holds the value N = sqrt(AME_NELEM), the side length of an AME tile in elements.

The value is a design-time constant equal to the square root of
`AME_NELEM`.
Because `AME_NELEM` is always a power of 4, N is always a power of 2.

Software reads this CSR once at function entry to obtain N, then uses
N to derive all tile loop bounds and memory strides without hardcoding any
implementation-specific constants.
This is analogous to reading `vlenb` in RISC-V Vector code.


|===
| Field | Location | Description

| VALUE
| `XLEN-1:0`
| Tile side length (N)

|===

[#ame:doc:csr:ameudsz]
==== ameudsz

Holds `AME_UNIT_DATATYPE_SIZE`, the element size in bits at which exactly one
square fits in a single M register.

The value is a design-time constant.  Software reads this CSR together with
a datatype encoding to compute the *group size*: the number of consecutive M
registers required to hold one square:

  group_size = max(1, ceil(dtype_size_bits / AME_UNIT_DATATYPE_SIZE))

where `dtype_size_bits` is bits [7:0] of the 32-bit datatype encoding.
Packed datatypes use one M register and therefore have `group_size = 1`.
When `group_size > 1`, the register index used with any instruction must be a
multiple of `group_size`.

This CSR is analogous to `vlenb` in RISC-V Vector code: software reads it
once at function entry to derive all register-grouping and stride calculations
without hardcoding any implementation-specific constant.


|===
| Field | Location | Description

| VALUE
| `XLEN-1:0`
| Unit datatype size (AME_UNIT_DATATYPE_SIZE) in bits

|===

[#ame:doc:csr:amefflags]
==== amefflags

`amefflags` holds the accrued floating-point exception flags raised by AME
floating-point operations.  The low 5 bits have the same meaning as the
`fflags` CSR of the RISC-V F extension.  An AME floating-point operation that
raises an exceptional condition sets the corresponding flag bits; flags
accrue (are never cleared by hardware) until software clears them by writing
the CSR.  Flag updates from an executing instruction are staged and commit
atomically with the instruction's destination writes; an instruction that
raises a synchronous exception does not update `amefflags`.  Reserved bits are
WPRI and read as zero.

The CSR resets to zero.  It is hart state and must be saved and restored with
the AME state when software changes execution context.  AME operations do not
modify the `fflags` CSR of the F extension.

|===
| Field | Location | Description

| NV
| `4`
| Invalid operation

| DZ
| `3`
| Divide by zero

| OF
| `2`
| Overflow

| UF
| `1`
| Underflow

| NX
| `0`
| Inexact

|===

[#ame:doc:csr:amexsat]
==== amexsat

`amexsat` reports fixed-point saturation from AME integer operations.  Bit 0 is
the sticky saturation flag `SAT`.  `SAT` is set only when an integer
operation whose destination datatype has `Saturation=1` clamps (saturates) an
out-of-range result to the destination range; operations that do not saturate
their output leave `amexsat` unchanged.  Destinations with `Saturation=0` never
update `amexsat`.  `SAT` remains set until software clears it by writing the
CSR.  Flag updates from an executing instruction are staged and commit
atomically with the instruction's destination writes; an instruction that
raises a synchronous exception does not update `amexsat`.  Reserved bits are
WPRI and read as zero.

The CSR resets to zero.  It is hart state and must be saved and restored with
the AME state when software changes execution context.

|===
| Field | Location | Description

| SAT
| `0`
| Fixed-point saturation flag.  Set when a saturating integer operation
clamps its output to the destination datatype's range.

|===

[#ame:doc:csr:amestatus]
==== amestatus

[#ame:doc:csr_field:amestatus:UN]
`amestatus` is backend context state and reports sticky AME execution status.
It resets to zero. Software
clears a reported condition by writing zero to the corresponding bit; writing
one leaves that bit set.  Reserved bits are WPRI and read as zero.


|===
| Field | Location | Description

| UN
| `0`
| Unsupported-operation flag.  An implemented AME instruction sets `UN` when
its datatype or operation tuple is unsupported.  The instruction makes no
other architectural state change in that case.  `UN` remains set until
software clears it.

|===
