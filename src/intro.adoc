== Introduction

The Attached Matrix Extension (AME) adds instructions to accelerate tensor codes at the heart of many machine learning and HPC applications. It has the following goals:

Scalable::
*  AME targets markets ranging from low-power embedded edge to datacenter and HPC.
*  Due to the extreme range of target designs, some AME implementation parameters affect binary compatibility. Thus, code compiled for one AME implementation may not run another, though profiles are expected to constrain parameters so that binaries are compatible within a market.

Isolated::
*  AME is designed to work well on tensor codes regardless of whether the host hart implements RISC-V Vector (RVV). Implementing RVV is not a prerequisite of AME. Frequently moving state between RVV and AME may degrade performance on some implementations.

Detachable::
*  AME resources may be dedicated to a hart or shared among harts. Sharing can
   improve utilization and reduce area and power. Ownership is independent of
   the physical resource topology; see <<shared-ame-backend>>.


=== Specification status

This specification is an active draft. The instruction definitions and
programming-model rules in this document describe the current architecture.
The following architectural questions remain open:

* A formal definition of the ordering relationship between AME and non-AME
  memory operations. The current requirements are described in
  <<ame-consistency-model>>.
Prefix and reduction instructions do not support widening
source-to-destination datatype tuples in the current architecture. Their
source and destination datatypes must be identical, as specified in
<<ame-common-operand-classes>>.
